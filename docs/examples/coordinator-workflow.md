# 使い方の例: コーディネーターと作業エージェントで開発を進める

pitboard の作者が、pitboard 自身を作るときに取った進め方の記録。**個人の使い方の一例であって、pitboard の決まりではない。** 道具の説明 (`pitboard -h`) や skill には含めていない。

人は pitboard だけを見て、コメントと `y` / `n` で方向を決める。AI は 3 体: 人と話して段取りをするコーディネーター、実装する builder、確かめる reviewer。エージェントの管理には herdr を使った。

## 役割

- **人**: pitboard だけを見る。コメントと `y` / `n` で方向を決める
- **コーディネーター (人と会話している AI)**: pitboard に書くことと、段取りが仕事。自分では実装しない
- **開発エージェント (builder)**: 実装する
- **レビューエージェント (reviewer)**: 実装者の「確かめた」を信じず、自分で動かして確かめる。コードは直さない

## コーディネーターがすること

- **設計を決める**: 人のコメントを、何をなぜ作るかの依頼書にする。依頼書には人の言葉をそのまま引く
- **依頼はファイルで渡す**: 依頼書を repo に置き、エージェントにはパスだけ伝える。結果もファイルに書かせ、要る所だけ読む
- **エージェントのコンテキストを管理する**: 依頼は 1 件で完結させる。別の仕事に移る前に、エージェントの会話を消す。レビュー役は毎回消す
- **1 体に任せすぎると、元の依頼がいつまでも終わらない**: 足すかどうかは、元の依頼の完了までの時間がどれだけ延びるかで決める (2 つを 1 体に任せたほうがぶつかりが少なく速いこともある)。すぐ出さない依頼の待ち行列はコーディネーターが持ち、pitboard の畳んだ節に置く (人の目には入れない)
- **レビューの結果を仕分ける**: 指摘ごとに直し方を決めて、開発エージェントへの依頼書にする
- **区切りで取り込む**: テストを通し、コミットし、実行ファイルを置き換え、開き直しを人に知らせる
- **エージェントの終わりを見張る**: 依頼したら、結果のファイルができるのを裏で待つ。人に声をかけられるまで止まっていてはいけない
- **pitboard を保つ**: 届いた入力への返事、進み具合、決まったことを書く。解決した答えは落とす

## 置き場所

- **エージェント**: herdr の workers タブ。会話のタブにはペインを足さない
- **依頼書と結果**: repo の `docs/dev/`

## 人からのフィードバック (2026-11-23 から。人の言葉 → それで決めたこと)

### 分担と置き場所

- 「実装用のエージェントを herdr で管理し、人は設計議論に集中しようか」「実装モデルは opus で」 → AI は設計と段取り、実装は builder
- 「会話しているペインがどんどん小さくなっちゃう」 → エージェントは別のタブに置く。会話のタブにペインを足さない
- 「エージェントたちのコンテキスト効率もケアしようね」 → 依頼はファイルで渡す、1 件で完結させる、別の仕事の前に会話を消す
- 「全体的な整合チェックみたいなのをレビュアーにお願いしてもいいかも」 → 文書の整合は、確認役に定期的に見させる
- 「エージェント間のコミュニケーションは人間が理解できなくても良いため、方法、および、言語は問わない。作業の精度とコンテキスト効率の観点で最適な方法を自由に選んでほしい」 → 依頼書と結果は、人が読む前提をやめる。AI どうしで正確かつ短く伝わる形で書く (人に見せるのは pitboard だけ)
- 「要らなくなったエージェントとかは閉じていいからね。そのあたり注意できてる？」 → 依頼が済んで結果を取り込んだら、そのエージェントのペインと作業場所 (worktree) をその場で片付ける。次の用が見えているものだけ残す

### 判断の基準

- 「試作がそのまま使える、みたいな easy さを判断根拠にしてはいけない。あるべきに近づくように」 → 作る側の都合で設計を選ばない
- 「再発防止はできそう？できるだけ忘却しないように注意、みたいな方法ではなく」 → 落ち度の対策は、AI の注意ではなく、道具か手順の仕組みにする
- 「それが何回も行われるとコンテキスト効率に悪い気もする」 → AI に毎回見せるものは、1 行に収める

### pitboard の使い方

- 「席に戻ったときに pitboard だけを見られるようにしたい」 → 質問への答えも、進み具合も、pitboard に書く
- 「解決したと思うものは人が勝手に消していいよ」 → 解決した答えは AI が落とす
- 「claude code もセッション上で返答しなくてよくなったかも」「セッションには問答を書かなくてもいい」 → チャットは 1 行だけ
- 「コマンドが新しくなって再起動が必要なときはちゃんと教えてほしい」 → 開き直しは、お知らせで伝える
- 「lint 的なものをかけたほうがいいんじゃないか？人の方でも」 → 報告を書き換えたら必ず検査を通す。道具も誤りを知らせる
- 「pitboard だけ見るとちゃんと queue に積まれているのかどうか不安になります」 → 「進行中」は、頼まれたこと 1 つにつき 1 行。依頼書の単位でまとめない
- 「これってまだ解決してないの？」 → 入れたら、答えの行とコメントの状態をその場で直す。道具が残りを毎回見せる

### 進み方

- 「まだ作業は続いてるんですか？？なぜ止まっている？」 → エージェントに依頼したら、終わりを必ず見張る
- 「最近は実装のスピードが落ちてきたような気が」 → 時間の読めない調査は確認役に回す。依頼は小さく切って、できた順に入れる
- 「一人のエージェントにどんどん仕事を任せると責務が広がりいつまでも仕事が終わらないということは起きないだろうか。引き継ぎ不要という価値もあるかもしれないが、そのあたりのタスクキューマネージャー的な役割りはあなたが果たすべきだと思うぞ」「1 builder 1タスクは状況に依ると思う。…具体的な手順ではなく、一人になんでも任せすぎるとオリジナルのタスクの完了リードタイムが無限に広がることに気をつける、といった目的ベースの書き方にしたいかな」 → 足すかどうかは元の依頼の完了までの時間で決める。待ち行列はコーディネーターが持ち、pitboard の畳んだ節に置く
- 「終わったら試しにつけてみてね」 → 新しい部品が入ったら、AI が実際にこの報告で使って見せる

### AI が自分で見つけた落ち度

- 依頼書を書き換えたのに builder に伝えなかった (2 回) → 書き換えと連絡を、1 つのコマンドで実行する
- 人のコメントの `>` を画面の不具合と読み違え、調査に時間を使わせた → 不具合と決める前に、画面の写真か再現の手順を確かめる
